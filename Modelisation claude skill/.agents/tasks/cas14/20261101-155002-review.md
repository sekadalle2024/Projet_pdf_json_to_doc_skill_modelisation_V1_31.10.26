# Cas 14 FRAP/Recommandations Python Implementation

Two Python scripts that convert FRAP audit JSON data to Word documents with bordeaux-themed styling. The converter (`json2word_frap.py`) handles 6-table structures with vertical metadata tables and horizontal content tables. The orchestrator (`execute_cas14_production.py`) pulls JSON from an N8N webhook and batch-processes multiple FRAP entries.

This is a standalone skill implementation following patterns from Cas 2/3/6 but with a unique bordeaux color (#8B0000) and dynamic table rendering. Tables 2-6 adapt to JSON structure: single-key dicts render as one-column tables, multi-key dicts as vertical tables, and lists as horizontal grids.

**Watch for:** Missing table 1 column width enforcement (likely); bullet point rendering inconsistency between formats (confirmed); lack of verification evidence from the coder (confirmed); no explicit test of landscape orientation (confirmed); missing error handling for malformed table structures (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The converter correctly implements the 6-table structure with Table 1 as vertical metadata (2 columns, first column bordeaux #8B0000) and Tables 2-6 as content tables that adapt to JSON structure. The landscape A4 orientation, bordeaux header/footer, and filename format with timestamp are all present.

The orchestrator follows the established pattern from Cas 2: call N8N webhook, extract Data_integrale with nested structure handling, save full response for audit trail, then loop through each FRAP and invoke the converter script with subprocess. It provides detailed logging with UTF-8 console reconfiguration for Windows.

Five blocking issues prevent approval: the coder provided no verification evidence (no test output, no Word document inspection report, no validation against the 6-table structure); Table 1 column widths are set incorrectly using Inches conversion instead of the specified twips values; bullet point rendering in `add_bulleted_lines` applies to all lines regardless of whether they start with "-", breaking non-bullet content; the converter processes only the first FRAP from JSON files containing multiple FRAPs without warning; and comprehensive error handling is missing for malformed JSON table structures.

## Six-table structure with vertical Table 1

Table 1 renders as vertical metadata (2 columns: Rubrique | Description) with column 1 having bordeaux background #8B0000 and white bold text. The implementation extracts table 1 from the JSON, calls `create_vertical_table`, and passes through all metadata fields.

Tables 2-6 use `create_horizontal_table` which branches on JSON structure: single-key dicts become 1-column tables (header + content), multi-key dicts become vertical tables, and lists become horizontal grids. This dynamic approach handles the FRAP schema where table 2 is `{"Intitule": "..."}`, table 4 is `{"Constat": "..."}`, etc.

The table iteration correctly identifies tables by the key pattern `"table N"` (case-insensitive) and skips table 1 for special handling. Spacing paragraphs are added between tables.

**Confirmed**: The column width implementation for Table 1 is broken. The code reads `col_widths = [4000, 11038]` (twips from the plan) but then does `cell.width = Inches(col_widths[0] / 1440)`. This divides twips by 1440 (the twips-per-inch ratio) to get inches, then passes to `Inches()` which multiplies by 914400 (EMUs per inch), producing a final width in EMUs that's off by a factor of 914400/1440 ≈ 635. The plan specifies 4000 twips for column 1; the code produces ~2.54M EMUs instead of ~57,150 EMUs. The correct approach is either `Inches(col_widths[0]/1440.0)` (but this is already done) OR `cell.width = col_widths[0] * 635` (twips to EMUs) OR setting widths at the table level before populating cells.

## Bordeaux #8B0000 color enforcement

The constant `BORDEAUX_RGB = RGBColor(0x8B, 0x00, 0x00)` correctly defines the Cas 14-specific bordeaux color (different from Cas 2/3/6's #7B1E3A). Applied to Table 1 column 1 background, Table 2-6 header backgrounds, document header (white text on bordeaux), and document footer text.

## Landscape A4 orientation

The page setup sets `section.page_width = Inches(11.69)` and `section.page_height = Inches(8.27)`, which are landscape A4 dimensions. Margins are set to top=0.5", bottom=0.46", left/right=0.38" (via `Inches()`). These match the twips values in the plan when converted: 1200 twips = 0.5 * 1440 twips/inch, etc.

No orientation enum is used. The spec calls for `section.orientation = WD_ORIENT.LANDSCAPE` but the code doesn't import or use this. Setting width > height achieves landscape implicitly, but the explicit orientation property should also be set for compatibility with Word's internal handling.

**Likely**: Missing explicit `section.orientation = WD_ORIENT.LANDSCAPE` could cause issues when Word opens the document and tries to reconcile orientation vs. dimensions. This should be added even though width/height are already swapped.

## Bullet point rendering with add_bulleted_lines

The function splits text on newlines, then for each line: if it starts with "-", strip the "-" and prepend "• "; otherwise, add the line as-is. All lines are added to the same paragraph with `\n` between them.

This logic has two issues:

1. Lines not starting with "-" are added without bullets, but they're still part of the same paragraph as the bulleted lines. This creates visual inconsistency: some lines have "• " prefix, others don't, all in one paragraph.

2. Multi-paragraph content without bullets (e.g., table 3 "Observation" with two paragraphs separated by `\n\n`) gets collapsed into a single paragraph with line breaks, losing the paragraph separation.

The spec shows that tables 4-6 contain bullet-point content ("- " prefixes in the JSON) while tables 2-3 contain narrative text. The current logic tries to handle both in one function, but it doesn't preserve structure for non-bullet text.

**Confirmed**: Bullet point rendering is inconsistent and will break narrative text formatting. The function should either (a) detect if the entire text block is bullet-list vs. narrative and apply different rendering, or (b) always render bullets if any line starts with "-", and treat non-bullet text as separate paragraphs.



## Filename format with timestamp

The filename is constructed as `f"{reference}-{etape_mission}- {software_name}_{timestamp}.docx"` where `reference` is extracted from table 1 or generated as `AUTO-HHMMSS`, `etape_mission` comes from table 1 "Etape de mission", and `timestamp` is `YYYYMMDD_HHMMSS` format. The space before "Logiciel" in `"- Logiciel..."` matches the spec's quirky format.

The sanitization step is missing. The plan mentions "Sanitize filename (remove invalid chars: `/:*?"<>|`)" but the code has no regex or `.replace()` calls to strip these characters. If `reference` or `etape_mission` contain slashes or colons, the filename will be invalid on Windows.

**Confirmed**: Filename format is correct but lacks sanitization for invalid characters.

## UTF-8 and Windows compatibility

Both scripts use `encoding='utf-8'` for all file operations. The orchestrator calls `sys.stdout.reconfigure(encoding='utf-8')` for Windows console output. The JSON parser uses `json.loads(content)` directly without specifying encoding, relying on the file read's encoding.

The `extract_json_from_text` function uses a regex to find the first JSON object, then `json.loads()`, but doesn't handle UTF-8 BOM. The plan mentions "Handle UTF-8 with BOM (`utf-8-sig`)" but the code doesn't use `utf-8-sig` anywhere.

**Possible**: If a JSON file has a UTF-8 BOM, the regex may fail or `json.loads()` may choke on the BOM bytes. Adding `encoding='utf-8-sig'` when reading JSON files would handle this.

## Error handling coverage

The converter's `main()` function wraps JSON parsing in a try-except but catches only generic `json.JSONDecodeError`. File I/O errors, KeyError from missing table 1 fields, and docx library errors are not caught. If table 1 is missing "Reference" or "Etape de mission", the code falls back to generated values, which is good, but if table 1 itself is missing, the code will crash with KeyError.

The orchestrator's `call_n8n_api` catches `Timeout`, `ConnectionError`, `HTTPError`, and `JSONDecodeError` specifically, logging each with actionable messages ("Vérifiez que N8N est démarré"). This is solid.

The `process_frap` function catches `TimeoutExpired` for subprocess calls and logs stderr on failure, but doesn't catch `FileNotFoundError` if the skill script is missing (this is checked before the loop, good) or JSON write errors.

**Confirmed**: Error handling in the converter is incomplete. Missing table validation and file I/O exception handling. The orchestrator's error handling is comprehensive.

## Single-FRAP processing in converter

The `generate_word_document` function searches for the first FRAP in `data_to_process` and stores it in `first_frap`, then processes only that FRAP. The comment says "Traiter uniquement le premier FRAP du JSON" (Process only the first FRAP from JSON). If the JSON contains multiple FRAPs (e.g., `exemple_frap_complet.json` with 3 FRAPs), only the first is converted, and the others are silently ignored.

This is intentional: the converter is designed to process one JSON file = one FRAP document. The orchestrator handles multiple FRAPs by saving each to a separate temp JSON file and invoking the converter multiple times. However, if a user runs the converter directly on a multi-FRAP JSON, they'll get only one document without warning. This could be confusing.

The plan says "For testing multiple FRAPs locally, would need to split `exemple_frap_complet.json` or use the orchestrator," acknowledging this limitation, but also says "Note: The orchestrator (`execute_cas14_production.py`) handles multiple FRAPs from N8N response," implying the converter itself doesn't need to handle multiple FRAPs. The spec doesn't clarify whether the converter should process all FRAPs or just one.

**Confirmed**: The converter processes only the first FRAP without logging a warning if multiple exist. This should either be documented clearly in the usage message or changed to log a warning when multiple FRAPs are detected.
